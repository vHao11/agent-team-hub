# 架构与关键行为

Agent Team Hub 提供跨组协作台账与共享能力目录。服务端保存业务事实，各成员的 harness 承担本机执行。代码采用独立服务与薄适配层，核心领域不依赖 DSH。

这是根据设计方案新建的实现；本次没有取得 Windows 本机的 HajimiWorkbench、个人待办看板和增强 Superagent 源码，不能将这里的接口描述为这些本机项目已经提供的接口。

## 组成

| 部分 | 作用 |
| --- | --- |
| `server/teamhub` | FastAPI、SQLAlchemy、SQLite，处理身份、事项、交付、运行和能力版本 |
| `web` | React 与 TypeScript 界面，调用真实 API |
| `packages/client` | 供 CLI、插件和其他客户端复用的 HTTP 客户端 |
| `packages` 下的 CLI 与 DSH 包 | 命令入口、能力安装以及宿主适配 |
| `server/teamhub/mcp_server.py` | MCP stdio 入口，通过相同 HTTP API 操作业务对象 |
| `examples` | 可试用的 Skill、脚本及接入示例 |
| `tests` | 隔离数据库上的行为验收测试 |

数据库位于服务端本地磁盘。成员通过 API 访问，不能把 SQLite 文件放在网盘或多人共同打开的目录里当同步协议。

## 业务对象

| 对象 | 权威边界 |
| --- | --- |
| WorkItem | 跨组目标、当前责任、约定期限、验收条件与生命周期 |
| LocalBinding | 共享事项与某台设备上的本地待办、工作区、会话之间的关联 |
| Run | 一次明确启动请求及执行端回报，不代表业务验收 |
| Delivery | 一个具体交付版本，保存成果摘要与可共享材料 |
| Review | 对指定交付的批准或退回 |
| CapabilityRelease | 固定版本的共享能力内容与安装声明 |
| TeamToolset | 本组后续执行推荐采用的能力版本集合 |

一个事项可以经历多次运行，再提交一次交付；人工工作也可以直接形成交付。个人待办完成和 Agent 成功都不会自动把事项置为已完成。

## 状态命令

事项的正常路径是 `open → accepted → active → review → done`。验收退回将 `review` 变为 `active`，取消进入 `cancelled`。阻塞原因独立保存，不会覆盖原生命周期。

首次发起后，请求组负责跟进，目标组存在于待接收字段。接单事务切换负责组和负责人。后续转交也先保留旧责任，接收组接受后才切换。

接单、开工、转交、交付、验收和取消使用明确命令。每条命令检查身份、对象版本和状态前置条件。普通客户端不能通过任意修改 `status` 绕开规则。

## 身份与权限

首版是一个共享协作空间：有效成员可以查看空间内的台账、目录和交付材料，不提供项目级隔离。请求身份由 Bearer 令牌解析，客户端传入的组 ID 或负责人 ID 本身不构成授权。

| 动作 | 业务权限 |
| --- | --- |
| 接受初始请求或转交 | 当前待接收组成员；负责人必须属于该组 |
| 开始处理、启动执行、提交交付 | 当前指定负责人 |
| 更新进展 | 当前负责组成员，或请求方、指定验收人 |
| 修改验收范围 | 请求方或指定验收人 |
| 验收交付 | 当前指定验收人，管理员身份不自动获得代验权 |
| 发布能力版本 | 能力维护团队成员，或管理员 |
| 维护团队工具集 | 本组组长，或管理员 |
| 添加团队、分发成员令牌 | 管理员 |

身份表保存令牌摘要；创建成员的幂等回执保存首次分发结果，所以服务端数据目录仍属于凭据保护边界。普通成员列表不返回令牌或摘要。演示身份接口只在显式演示空间启用，数据目录记录模式，避免演示令牌随启动参数切换进入正式空间。

## 并发与重试

关键写入使用三个不同标识：

- `operation_id`：标识一次用户意图。相同请求重试返回原结果，同一个 ID 携带不同内容会拒绝。
- `version`：保护事项更新。旧页面或并发修改需要先读取最新状态。
- `spec_revision`：标识需求及验收条件。进展、心跳等普通变化不应使交付范围变更。

SQLAlchemy 事务集中维护状态、操作回执和事件。SQLite 写操作使用 `BEGIN IMMEDIATE`，将读版本、判断前置条件及提交更新放进同一个写事务；两个承接者同时操作时只有一个有效接单。数据库唯一约束同时保护能力版本、交付序号、运行派发 ID、绑定身份和操作回执。

操作 ID 按成员身份保存，并将命令路径和规范化请求内容纳入一致性判断。相同成员拿同一个 ID 调用不同命令，或改变命令内容，会收到冲突。失败请求不会留下成功回执，修正输入后应使用新的操作意图标识；网络断开而结果不明时，应保留原 ID 查询或重试。

客户端收到事件只更新投影；重放事件不会再次启动 Agent。事件游标用于从上次位置拉取变化，不是命令编号。

## 交付验收

Delivery 逐次新增，不覆盖旧内容。负责人可以在处理中的 `active` 状态提交，也可以在待验收的 `review` 状态补交新版本。后一种情况更新当前交付指针，保留前一版材料；同一次提交的网络重试则通过 `operation_id` 返回原交付。验收同时检查：

1. 当前成员是指定验收人。
2. 事项仍处于待验收。
3. 该交付仍是当前交付版本。
4. 交付对应当前 `spec_revision`。

更改验收条件后需要重新提交。旧交付和原有验收历史继续保留，但旧页面的迟到批准不能关闭新版本。

交付引用使用接收方可访问的 HTTP(S) 地址或已上传的 `artifact://` 引用。本机绝对路径不算共享交付。附件下载仍要求成员身份。

服务端校验 HTTP(S) 地址结构及附件是否存在，不会替请求方验证外部链接的实际内容或访问权限；验收时仍应打开材料确认成果。上传的文件与数据库一起位于服务端数据目录，备份应覆盖完整目录。

## 执行语义

Run 从请求登记开始，分别记录 queued、starting、running、waiting_input、succeeded、failed、cancel_requested、cancelled 与 unknown。

运行回报携带单调递增的 `sequence`。重复或迟到消息不能把状态倒退；终态不能重新变成 running。回报只由该运行的请求身份和关联设备提交。

一个事项存在尚未确认结束的运行时，不能从另一设备重新启动。unknown 也占用该执行位置，避免把失联误当失败而重复执行。

创建运行保存当时的目标、验收条件、需求版本、责任代次和能力版本快照。执行回报不修改 WorkItem 版本；人工进展和 Agent 心跳互不制造乐观锁冲突。存在尚未结束的运行时，接收转交与提交交付也会被阻止，直到执行端确认结果或停止状态。

取消请求表示希望停止，执行端确认后才是 cancelled。已取消事项收到迟到运行结果时，可以留存结果，但不会恢复或完成该事项。

这套协议不声称对外部提交、发送消息等动作提供严格执行一次保证。宿主已经启动但句柄尚未持久保存时崩溃，需要查回既有运行；查不明时保持 unknown。

## 能力版本

能力发布版本唯一且不可覆盖，修改产生新版本。运行创建时解析显式指定能力或负责组工具集，并保存实际 release ID 与版本。团队随后升级推荐版本，不会改变已存在运行的记录。

安装包可以来自目录保存的固定版本。安装动作只负责获取和配置；执行脚本是独立的明确动作。Skill 的说明不会被当作平台无条件信任的宿主接口。

## 部署边界

首版面向单个协作空间和单服务实例。Web、CLI、MCP 使用相同身份和规则。演示身份仅在显式演示模式使用，正式数据目录初始化生成独立管理员令牌。

DSH 插件是否能够控制本机看板与增强 Superagent，取决于安装的适配器及实际宿主接口。未连接时应返回不可用状态，不能生成模拟成功回执。实际能力矩阵见 [集成边界](integration-gaps.md)。
